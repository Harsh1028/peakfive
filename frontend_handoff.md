## 1. Backend setup

You need Python 3.9 or newer. Run these from the repository root:

```bash
cd peakfive                       # repository root
python3 -m venv .venv             # one-time: create a virtual environment
source .venv/bin/activate         # Windows: .venv\Scripts\activate
pip install -r requirements.txt   # one-time: pulp, fastapi, uvicorn
uvicorn api.main:app --reload     # starts http://127.0.0.1:8000
```

Check that it's running:

```bash
curl http://127.0.0.1:8000/health
# {"status":"ok"}
```

Interactive API docs (generated by FastAPI) are at <http://127.0.0.1:8000/docs>.
They include a ready-to-run example request.

### Optional settings (environment variables)

These are read once at server start. Restart uvicorn after changing them.

| Variable | Default | Meaning |
|---|---|---|
| `PEAKFIVE_CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173,http://localhost:3000,http://127.0.0.1:3000` | Comma-separated browser origins allowed to call the API. `*` is rejected. See [§9](#9-connecting-from-vite--react-cors). |
| `PEAKFIVE_MAX_BODY_BYTES` | `262144` (256 KB) | Larger request bodies get HTTP 413. |
| `PEAKFIVE_MAX_CONCURRENT_SOLVES` | `2` | Extra simultaneous `/optimize` calls get HTTP 503. |

Example:

```bash
PEAKFIVE_CORS_ORIGINS="http://localhost:5173,http://localhost:4173" uvicorn api.main:app --reload
```

The server refuses to start, with a clear error message, if a value is invalid
(for example `PEAKFIVE_CORS_ORIGINS="*"` or `PEAKFIVE_MAX_BODY_BYTES=0`).

## 2. API endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | Liveness check. Returns `{"status": "ok"}`. |
| `POST` | `/optimize` | Builds a 24-hour pump schedule. |
| `POST` | `/compare` | Simulated conventional baseline vs optimizer on the **same** request body. See [§13](#13-baseline-vs-optimizer-comparison-post-compare). |
| `GET` | `/docs`, `/openapi.json` | FastAPI's built-in interactive docs and schema. |

There are no other endpoints. Nothing is stored between requests: each call is
independent.

### `POST /optimize`

- **Request:** `Content-Type: application/json`, body as in [§3](#3-request-format).
- **Response:** always JSON. The body has the same five fields for every
  outcome, including errors (one exception, for malformed JSON, is in
  [§4.3](#43-http-status-codes)).
- **Typical time:** 0.1–2 s for the illustrative system. Hard problems are
  capped at **30 s**, so set your UI timeout above 30 s, for example 45 s.

### 3.2 Field reference

Every field below is **required** unless marked optional.

| Field | Type | Rules / meaning |
|---|---|---|
| `date` | string | ISO date `YYYY-MM-DD`. Validated, but does not change the result. |
| `peak_window` | `["HH:MM","HH:MM"]` **or** `{"start_slot": int, "end_slot": int}` | The utility's peak period, half-open `[start, end)`. Times must be two-digit and on a 15-minute boundary (`"16:00"`, not `"4pm"` or `"16:10"`); `"24:00"` is allowed as an end. If start is after end, the window wraps past midnight (`["22:00","02:00"]`). If start equals end, the window is empty. |
| `system.slot_minutes` | integer | Must be exactly `15`. |
| `system.base_load_kw` | number ≥ 0 | Site load that is always on (lighting, controls, etc.). Included in every row's `kw`. |
| `system.tank.capacity_m3` | number ≥ 0 | Maximum volume. |
| `system.tank.initial_m3` | number ≥ 0 | Volume at 00:00. |
| `system.tank.min_operating_m3` | number ≥ 0 | Operational minimum. |
| `system.tank.fire_reserve_m3` | number ≥ 0 | Firefighting reserve, kept **on top of** the operating minimum. The tank may never drop below `min_operating_m3 + fire_reserve_m3`. |
| `system.pumps` | array (0–20 items) | See the pump fields below. |
| `pumps[].id` | non-empty string, unique | Shown in `pumps_on`. |
| `pumps[].kw` | number ≥ 0 | Electrical draw while ON. |
| `pumps[].flow_m3h` | number ≥ 0 | Flow into the tank while ON, in m³ per **hour**. One slot adds `flow_m3h × 0.25`. |
| `pumps[].min_run_slots` | integer ≥ 1 | Once started, the pump stays ON at least this many slots. `4` = 1 hour. |
| `pumps[].min_off_slots` | integer ≥ 1 | Once stopped, the pump stays OFF at least this many slots before restarting. |
| `pumps[].max_starts_per_day` | integer ≥ 0 | Maximum number of starts in the day. |
| `pumps[].available` | boolean | `false` means the pump stays OFF all day. |
| `system.demand_m3_per_slot` | array of exactly 96 numbers ≥ 0 | Water drawn from the tank in each 15-minute slot, in m³ per **slot** (not per hour). Index 0 = 00:00–00:15. |
| `events` | array (optional, 0–500 items) | Fire and pump-outage scenarios. See [§8](#8-emergency-simulations). Omit it or send `[]` for a normal day. |

Integers must be JSON integers: `4`, not `4.0`. Booleans must be `true` or
`false`, not strings. `NaN`, `Infinity`, negative values and numbers too large
to represent are rejected.

## 4. Response format

### 4.1 Fields

Every `/optimize` response has exactly these five top-level fields:

| Field | Type | Meaning |
|---|---|---|
| `status` | string | Outcome. See [§4.2](#42-status-values). **Check this first.** |
| `schedule` | array | 96 rows when `status` is `optimal` or `feasible_timeout`; otherwise `[]`. |
| `coincident_kw_before` | `null` | Always `null` in this version. See [§7](#7-peak-demand-metrics). |
| `coincident_kw_after` | number or `null` | Highest site kW in any peak-window slot. `null` when there is no schedule or the peak window is empty. |
| `explanation` | string | Readable summary: solve quality, assumptions, events applied, or why it failed. Safe to show to users; don't parse it. |

Each `schedule` row has exactly four fields:

| Field | Type | Meaning |
|---|---|---|
| `slot` | integer 0–95 | Slot index. Rows are always in order 0, 1, …, 95. |
| `pumps_on` | array of strings | IDs of the pumps running during this slot, in request order. `[]` = all off. |
| `kw` | number | Total site load in this slot: `base_load_kw` plus the `kw` of every pump in `pumps_on`. |
| `tank_m3` | number | Tank volume at the **start** of this slot. See [§6](#6-reading-reservoir-levels). |

Real response for the [§3.1](#31-complete-working-example-96-demand-values)
request (rows 3–93 cut for length):

<!-- verify: response-shape name=full -->
```jsonc
{
  "status": "optimal",
  "schedule": [
    {"slot": 0, "pumps_on": ["P2"], "kw": 80.0, "tank_m3": 850.0},
    {"slot": 1, "pumps_on": ["P2"], "kw": 80.0, "tank_m3": 850.85},
    {"slot": 2, "pumps_on": ["P2"], "kw": 80.0, "tank_m3": 851.7},
    // ... rows 3–93 ...
    {"slot": 94, "pumps_on": ["P1", "P2"], "kw": 160.0, "tank_m3": 815.1420000000005},
    {"slot": 95, "pumps_on": ["P1"], "kw": 110.0, "tank_m3": 840.9070000000005}
  ],
  "coincident_kw_before": null,
  "coincident_kw_after": 30.0,
  "explanation": "Proven optimal schedule. coincident_kw_after = max site kW (pumps + 30 kW base load) over the 16 peak-window slots. coincident_kw_before is null: the request defines no independent baseline schedule, so no before/after comparison is reported. tank_m3 is the volume at the start of each slot; end of day 850.5 m3 vs start 850.0 m3; minimum 491.4 m3 over all 97 boundaries (floor 450 m3 incl. fire reserve). Assumes all pumps OFF before 00:00 with min-off satisfied (a run at slot 0 counts as a start), and every run completes its min run before midnight."
}
```

Volumes are raw floating-point numbers (`840.9070000000005`), so round them for
display, for example with `v.toFixed(1)`.

### 4.2 Status values

| `status` | HTTP | Schedule? | What it means | Suggested UI |
|---|---|---|---|---|
| `optimal` | 200 | 96 rows | Best possible schedule, **proven**. | Show the schedule. |
| `feasible_timeout` | 200 | 96 rows | Hit the 30 s limit. The schedule is valid and checked against every rule, but not proven best. | Show the schedule with a "not proven optimal" badge. |
| `infeasible` | 200 | `[]` | No schedule can meet every rule (tank limits including fire reserve, pump limits, outages). This is a real answer, not a bug. | Show `explanation`, e.g. "Demand exceeds what the available pumps can supply." |
| `timeout_no_solution` | 200 | `[]` | Hit the 30 s limit before finding any valid schedule. It is unknown whether one exists. | Suggest simplifying the scenario or retrying. |
| `invalid_input` | 422 | `[]` | The request breaks the contract. `explanation` names the field, e.g. `"demand_m3_per_slot must be a list of exactly 96 numbers"`. | Show `explanation` near the form. |
| `invalid_input` | 413 | `[]` | Request body over 256 KB. | Shouldn't happen with normal requests (the full example is about 1.4 KB). |
| `error` | 503 | `[]` | Server busy: 2 solves are already running. Has a `Retry-After: 5` header. | Retry after 5 s, or show "busy". |
| `error` | 500 | `[]` | Unexpected internal failure. | Show a generic error. |

**Rule of thumb:** draw a schedule only when `schedule.length === 96`, which
happens only for `optimal` or `feasible_timeout`. The backend never returns a
partial or unverified schedule.

### 4.3 HTTP status codes

| HTTP | Body shape | When |
|---|---|---|
| 200 | PEAKFIVE contract (5 fields) | `optimal`, `feasible_timeout`, `infeasible`, `timeout_no_solution` |
| 413 | PEAKFIVE contract | Body too large |
| 422 | PEAKFIVE contract | Valid JSON object that breaks the request rules |
| 422 | **FastAPI default:** `{"detail": [...]}` | Body is not JSON, or is JSON but not an object (e.g. an array). This is the one case without the 5-field shape. |
| 500 | PEAKFIVE contract | Internal error |
| 503 | PEAKFIVE contract + `Retry-After` header | Too many simultaneous solves |

## 5. Reading the pump schedule

The day is split into **96 slots of 15 minutes**. Slot `t` covers
`[t × 15 min, (t + 1) × 15 min)`:

| Slot | Time |
|---|---|
| 0 | 00:00–00:15 |
| 4 | 01:00–01:15 |
| 64 | 16:00–16:15 (start of the example peak window) |
| 79 | 19:45–20:00 (last slot of the example peak window) |
| 95 | 23:45–24:00 |

```ts
const slotLabel = (slot: number) => {
  const m = slot * 15;
  return `${String(Math.floor(m / 60)).padStart(2, "0")}:${String(m % 60).padStart(2, "0")}`;
};
// slotLabel(64) === "16:00"
```

- A pump is **ON for the whole slot** if its ID is in that row's `pumps_on`.
  There are no partial slots.
- Energy for one slot (kWh) = `kw × 0.25`.
- Suggested visualisations: a Gantt-style row per pump (ON/OFF bars), a
  stepped `kw` line, and a `tank_m3` line ([§6](#6-reading-reservoir-levels)).
  Shade slots in `peak_window`.

Rules every returned schedule obeys:

- Pumps are assumed **OFF before 00:00**. A pump ON at slot 0 counts as a start.
- Every run lasts at least `min_run_slots` and **finishes before midnight**.
- Between two runs of the same pump there are at least `min_off_slots` OFF
  slots. A pump may stay off at the end of the day without meeting
  `min_off_slots`.
- Number of starts ≤ `max_starts_per_day`.
- Unavailable pumps and pumps in an outage window are never ON.

Actual pattern for the [§3.1](#31-complete-working-example-96-demand-values)
request (`#` = ON, one character per slot, starting at 00:00). Note that both
pumps are OFF throughout 16:00–20:00:

```
P1: .............................................######.............................################
P2: ###############################################################.................###############.
```

## 6. Reading reservoir levels

**`tank_m3` is the volume at the START of the slot**, before that slot's
pumping and demand. So:

- `schedule[0].tank_m3` always equals `system.tank.initial_m3`.
- `schedule[t + 1].tank_m3 = schedule[t].tank_m3 + 0.25 × Σ flow_m3h (pumps ON in t) − demand[t]`,
  where `demand[t]` includes any fire-event extra demand.

The **end-of-day volume (24:00) is not a row**. If you want to show it, compute
it from the last row with the same formula:

```ts
const last = schedule[95];
const inflow = last.pumps_on.reduce((s, id) => s + 0.25 * flowById[id], 0);
const endOfDay = last.tank_m3 + inflow - demandIncludingFire[95];
```

The backend guarantees end of day ≥ `initial_m3` (the tank doesn't drain over
the day). `explanation` also states the end-of-day value for display.

Horizontal reference lines worth drawing:

| Line | Value in the example |
|---|---|
| Capacity (`capacity_m3`) | 1200 m³ |
| Hard floor (`min_operating_m3 + fire_reserve_m3`) | 200 + 250 = **450 m³** |
| Operating minimum alone (`min_operating_m3`) | 200 m³; the fire reserve sits between 200 and 450 |

The tank stays between the hard floor and capacity at every slot boundary,
00:00 through 24:00.

## 7. Peak demand metrics

### `coincident_kw_after`

The **highest total site kW (pumps + base load) in any slot inside
`peak_window`**, in the returned schedule. In the example it is `30.0`: all
pumps are off during 16:00–20:00, so only the 30 kW base load remains.

The optimizer minimises energy use, weighting slots inside the peak window
10× more than slots outside it. It also penalises the peak-window maximum
and each pump start. So it tends to fill the tank before the peak window and
coast through it.

### `coincident_kw_before` is always `null`

A before/after comparison needs a baseline schedule ("what the operators would
have done"). The request has no field for one, and the backend doesn't invent
one. So there is **no before value, and no savings figure in kW, kWh or
dollars**.

In the UI:

- Show `coincident_kw_after` on its own, labelled e.g. "Peak-window demand
  (optimized)".
- Don't compute or display savings, percentages or costs from these numbers.
  The response has no tariff data and no baseline.
- Treat a non-null `coincident_kw_before` as a future feature. It is `null` in
  this version.
- For a before/after view, call `POST /compare` instead ([§13](#13-baseline-vs-optimizer-comparison-post-compare)).
  It returns a simulated conventional baseline alongside the optimizer, with
  its own display rules. `/optimize` itself is unchanged.

## 8. Emergency simulations

Add items to `events`. Time spans are **half-open `[start, end)`** in slots
(0 = 00:00, 95 = 23:45) and are **cut off at midnight**. Each event needs a
start and an end:

| Start (first match wins) | End (first match wins) |
|---|---|
| `start_slot`: integer 0–95 | `end_slot`: integer > start |
| `start`: `"HH:MM"` | `end`: `"HH:MM"` (may be `"24:00"`) |
| | `duration_slots`: integer ≥ 1 |
| | `duration_minutes`: integer, multiple of 15 |

Every field that is present is validated, even if a higher-priority field
overrides it. Unknown `type` values are rejected with 422.

### 8.1 Fire event

Adds `extra_m3_per_slot` m³ of demand to **every** slot in the span.
Overlapping fire events add together. `demand_m3_per_slot` is accepted as an
alias of `extra_m3_per_slot`.

Replace `"events": []` in the [§3.1](#31-complete-working-example-96-demand-values)
request with:

<!-- verify: events name=fire expect_http=200 expect_status=optimal -->
```json
"events": [
  {"type": "fire", "start": "17:00", "end": "19:00", "extra_m3_per_slot": 30}
]
```

Result: `optimal`. The optimizer fills the tank before the fire, reaching
about 1,115 m³ by 16:00. `explanation` ends with `"Fire demand added in 8 slot(s)."`

The fire reserve is a hard floor **even during a fire**. A fire that would
need it is reported as `infeasible`, not allowed to drain into the reserve.
For example, this request is `infeasible`:

<!-- verify: events name=fire_too_big expect_http=200 expect_status=infeasible -->
```json
"events": [
  {"type": "fire", "start_slot": 64, "end_slot": 72, "extra_m3_per_slot": 200}
]
```

### 8.2 Pump outage

Forces one pump OFF for the span.

<!-- verify: events name=outage expect_http=200 expect_status=optimal -->
```json
"events": [
  {"type": "pump_outage", "pump_id": "P1", "start_slot": 24, "end_slot": 48}
]
```

Result: `optimal`, with P1 off from 06:00 to 12:00 (slots 24–47; slot 48 may
run again). `explanation` ends with `"Outages forced OFF: P1 (24 slots)."`
`pump_id` must match a pump in `system.pumps`. An unknown ID gives 422.

### 8.3 Combined scenario

Events can be combined and written in any of the supported forms:

<!-- verify: events name=combined expect_http=200 expect_status=optimal -->
```json
"events": [
  {"type": "pump_outage", "pump_id": "P2", "start": "05:00", "duration_minutes": 120},
  {"type": "fire", "start_slot": 70, "duration_slots": 4, "extra_m3_per_slot": 25}
]
```

### 8.4 Taking a pump out for the whole day

Set `"available": false` on the pump instead of adding an outage event. With
the example system, losing P1 all day makes the day `infeasible`: demand is
1,817 m³, but P2 can supply at most 1,560 m³. `explanation` reports both
numbers.

## 9. Connecting from Vite / React (CORS)

Browsers block calls from your dev server (e.g. `http://localhost:5173`) to the
API (`http://127.0.0.1:8000`) unless the API allows that origin.

**Vite dev server (`npm run dev`, port 5173):** already allowed by default, on
both `http://localhost:5173` and `http://127.0.0.1:5173`. No backend changes
needed.

**Other ports or deployed frontend:** add the exact origin (scheme + host +
port, no path) and restart uvicorn:

```bash
# vite preview uses port 4173; add your deployed URL too
PEAKFIVE_CORS_ORIGINS="http://localhost:5173,http://localhost:4173,https://your-dashboard.example.org" \
  uvicorn api.main:app --reload
```

Setting `PEAKFIVE_CORS_ORIGINS` **replaces** the defaults, so list every
origin you need. Wildcards (`*`) are refused. The API allows `GET` and `POST`
with a `Content-Type` header, without cookies or credentials.

The origin your browser sends must match exactly: `http://localhost:5173` and
`http://127.0.0.1:5173` are different origins. If the browser console shows a
CORS error, compare the origin in the console with `PEAKFIVE_CORS_ORIGINS`.

**Alternative: Vite proxy (no CORS needed in dev).** In `vite.config.ts`:

```ts
export default defineConfig({
  server: { proxy: { "/api": { target: "http://127.0.0.1:8000", rewrite: (p) => p.replace(/^\/api/, "") } } },
});
```

Then call `fetch("/api/optimize", ...)` from the app.

### Example client

```ts
const API_BASE = import.meta.env.VITE_PEAKFIVE_API ?? "http://127.0.0.1:8000";

export async function runOptimizer(request: OptimizeRequest): Promise<OptimizeResponse> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), 45_000); // solver cap is 30 s
  try {
    const res = await fetch(`${API_BASE}/optimize`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(request),
      signal: controller.signal,
    });
    const body = await res.json();
    if (!("status" in body)) {
      // FastAPI's own 422 for non-JSON or non-object bodies: {"detail": [...]}
      throw new Error("Malformed request body");
    }
    if (res.status === 503) {
      // body.status === "error"; retry after Retry-After seconds (5)
    }
    return body as OptimizeResponse; // check body.status and schedule.length === 96 before drawing
  } finally {
    clearTimeout(timer);
  }
}
```

## 11. Limitations

### Illustrative data vs. real municipal data

| Item | Status |
|---|---|
| Pumps P1/P2 (80 kW / 100 m³/h, 50 kW / 65 m³/h), min run/off, max starts | **Illustrative** |
| Tank: 1200 m³ capacity, 850 m³ initial, 200 m³ operating minimum, 250 m³ fire reserve | **Illustrative** |
| 30 kW base load | **Illustrative** |
| The 96-value demand curve (morning and evening peaks) | **Illustrative**, a smooth synthetic shape |
| Peak window 16:00–20:00 | **Illustrative** example |
| Date `2025-07-15` | Label only. The backend uses no weather, calendar or utility data. |

**No real Ontario municipal, utility or tariff data is included in the
backend.** If the dashboard shows these numbers, label them as a demo or
illustrative scenario, e.g. a banner reading "Illustrative system — not real
utility data". If real data is used later, it must come from the data pipeline
and be sent in the same request format.

### Model limitations

- **No savings or cost figures.** `/optimize` has no baseline
  (`coincident_kw_before` is `null`) and there is no tariff input. `/compare`
  reports only a *simulated* peak-window kW difference against a simulated
  conventional policy ([§13](#13-baseline-vs-optimizer-comparison-post-compare)),
  never financial or measured savings.
- **Simplified hydraulics.** One tank and constant pump flow and power. No pipe
  pressure, pump curves, variable-speed drives or water quality. Not a
  hydraulic safety tool.
- **Fire reserve is never used**, even during a fire. Large fires are reported
  `infeasible` rather than drawing on the reserve.
- **No state carried between days.** Pumps are assumed OFF before midnight, and
  every run finishes before midnight.
- **Objective weights are untuned.** The 10× peak weighting and the start
  penalty are placeholders, not utility rates.
- **Timing.** Hard scenarios can take up to 30 s and may return
  `feasible_timeout`. Near that limit, results can vary with machine speed.
- **Capacity.** At most 2 solves at once per server process (HTTP 503 beyond
  that). No authentication and no rate limiting beyond this: it's suitable for
  demos and local use, not for exposure to the public internet as-is.

## 12. Appendix

### 12.1 TypeScript types

These match the backend contract. `OptimizeStatus` lists every value the API
can return.

```ts
export type HHMM = string; // "HH:MM", 15-minute aligned

export interface Pump {
  id: string;
  kw: number;
  flow_m3h: number;
  min_run_slots: number;      // integer >= 1
  min_off_slots: number;      // integer >= 1
  max_starts_per_day: number; // integer >= 0
  available: boolean;
}

interface EventSpan {
  start_slot?: number; start?: HHMM;                   // one required
  end_slot?: number; end?: HHMM;                       // one of these four required
  duration_slots?: number; duration_minutes?: number;
}
export interface FireEvent extends EventSpan {
  type: "fire";
  extra_m3_per_slot: number; // alias: demand_m3_per_slot
}
export interface PumpOutageEvent extends EventSpan {
  type: "pump_outage";
  pump_id: string;
}
export type PeakfiveEvent = FireEvent | PumpOutageEvent;

export interface OptimizeRequest {
  date: string; // YYYY-MM-DD
  peak_window: [HHMM, HHMM] | { start_slot: number; end_slot: number };
  system: {
    slot_minutes: 15;
    pumps: Pump[];
    tank: { capacity_m3: number; initial_m3: number; min_operating_m3: number; fire_reserve_m3: number };
    base_load_kw: number;
    demand_m3_per_slot: number[]; // exactly 96
  };
  events?: PeakfiveEvent[];
}

export type OptimizeStatus =
  | "optimal" | "feasible_timeout" | "infeasible"
  | "timeout_no_solution" | "invalid_input" | "error";

export interface ScheduleRow {
  slot: number;       // 0..95
  pumps_on: string[];
  kw: number;         // base load + running pumps
  tank_m3: number;    // volume at START of slot
}

export interface OptimizeResponse {
  status: OptimizeStatus;
  schedule: ScheduleRow[];           // 96 rows or []
  coincident_kw_before: null;        // no baseline in this version
  coincident_kw_after: number | null;
  explanation: string;
}
```

### 12.2 Validation limits

| Limit | Value |
|---|---|
| Request body | 256 KB (HTTP 413 above) |
| Pumps | 0–20 |
| Events | 0–500 |
| Demand values | exactly 96, each finite and ≥ 0 |
| `slot_minutes` | exactly 15 |
| Time strings | `"HH:MM"`, two digits each, minutes ∈ {00, 15, 30, 45}, `"24:00"` allowed |
| Simultaneous solves | 2 per server process, shared by `/optimize` and `/compare` (HTTP 503 above) |
| Solver time limit | 30 s |

Tank values that are valid numbers but physically inconsistent (e.g. the
initial volume is below the hard floor, or the floor is above capacity) return
`infeasible` (HTTP 200), not 422.

## 13. Baseline vs optimizer comparison (`POST /compare`)

`POST /compare` runs two schedules on **the same request body** and checks both
with the independent checker:

1. **Baseline:** a *simulated* conventional control policy. It switches pumps on
   reservoir level alone, with an end-of-day recovery rule, and ignores the
   peak window.
2. **Optimized:** exactly what `POST /optimize` returns for that body.

> **What this is not.** The baseline uses **illustrative, unvalidated
> settings**. It is **not actual Hamilton utility operations**, and nothing in
> the response is measured data or a financial saving. Show the response's
> `label` and `caveats` wherever the comparison appears.

Baseline policy, fixed in the backend (the frontend can't change it):

| Role | Pump | Start when | Stop when |
|---|---|---|---|
| Lead | lowest kWh/m³ usable pump (P2 in the example) | tank ≤ 650 m³ | tank ≥ 950 m³ |
| Backup | next pump (P1) | tank ≤ 550 m³ | tank ≥ 650 m³ |
| Recovery, 20:00–24:00 | both | tank < start volume + 25 m³ | lead ≥ 950 m³, backup ≥ start + 25 m³ |

Every start and stop, including backup and recovery starts, obeys minimum
run/off times, start limits, availability and outages. Full details are in
[`docs/baseline.md`](baseline.md).

### 13.1 Request

Same headers and body as `/optimize` ([§3](#3-request-format)), with no extra
fields:

```bash
curl -s -X POST http://127.0.0.1:8000/compare \
  -H "Content-Type: application/json" \
  --data-binary @peakfive_request.json
```

- **Size:** about 16 KB (both 96-row schedules).
- **Typical time:** about 0.4 s for the example. It runs one optimizer solve, so
  harder scenarios can take up to the 30 s limit (and return
  `optimized.status: "feasible_timeout"`). Keep the same 45 s client timeout.

### 13.3 Field reference

| Field | Type | Meaning |
|---|---|---|
| `status` | string | See [§13.5](#135-status-values-and-http-codes). |
| `label` | string | **Always display.** Says the comparison is simulated, not Hamilton operations, and not savings. |
| `explanation` | string | Why a comparison is or isn't available. |
| `peak_window` | object \| `null` | Present only when `status` is `comparison_available`. |
| `peak_window.baseline_kw`, `.optimized_kw` | number \| `null` | Highest site kW (pumps + base load) in any peak-window slot. `null` if the peak window is empty. |
| `peak_window.reduction_kw` | number \| `null` | `baseline_kw − optimized_kw`. **Can be negative** (the optimizer is higher); show it as is. |
| `peak_window.reduction_pct` | number \| `null` | `reduction_kw ÷ baseline_kw × 100`, unrounded. `null` if the peak window is empty or `baseline_kw` is 0. |
| `energy` | object \| `null` | kWh figures. Present only when `status` is `comparison_available`. |
| `energy.optimized_minus_baseline_kwh` | number | Note the sign: optimized **minus** baseline (opposite direction to `reduction_kw`). |
| `energy.optimized_minus_baseline_end_of_day_m3` | number | The end-of-day volume difference behind most of the kWh difference. |
| `energy.note` | string \| `null` | The stored-water caveat. Show it with any kWh figure. |
| `baseline.applicable` | boolean | `false` when the fixed thresholds don't fit the tank (e.g. capacity below 950 m³). Then `schedule` is `[]` and `metrics` is `null`. |
| `baseline.valid`, `optimized.valid` | boolean | `true` only if that schedule passed the independent checker. |
| `baseline.violations`, `optimized.violations` | string[] | The checker's messages (or the reason there is no schedule). |
| `*.metrics` | object \| `null` | `peak_window_kw`, `pump_energy_kwh`, `site_energy_kwh` (incl. base load), `min_tank_m3` (all 97 boundaries), `end_of_day_m3`, `initial_m3`, `pump_starts`, `pump_slots_on`. Both sides are computed the same way. |
| `*.schedule` | ScheduleRow[] | 96 rows, same row format as `/optimize` ([§5](#5-reading-the-pump-schedule)): `tank_m3` is the **start**-of-slot volume. `[]` when there is no schedule. |
| `optimized.status` | string | The `/optimize` status (`optimal`, `feasible_timeout`, `infeasible`, `timeout_no_solution`). |
| `optimized.explanation` | string | The `/optimize` explanation, verbatim. Its sentence "coincident_kw_before is null … no baseline" refers to `/optimize`; don't show it in the comparison view. |
| `caveats` | string[] | **Always display.** If the optimizer hit its time limit, an extra caveat says it isn't proven optimal. |

### 13.4 Response: comparison unavailable

If **either** schedule fails the checker or doesn't exist, the response still
has HTTP 200, but `peak_window` and `energy` are `null`. Any schedules that do
exist are still returned so they can be shown, without reduction figures.

A real example: the §3.1 request with P2 `"available": false`, shortened:

```json
{
  "status": "comparison_unavailable",
  "explanation": "No comparison reported: the baseline schedule failed the independent checker. Reduction figures would not be defensible. See each schedule's violations.",
  "peak_window": null,
  "energy": null,
  "baseline": {
    "applicable": true,
    "valid": false,
    "violations": ["final volume is below initial volume"],
    "metrics": {"peak_window_kw": 110.0, "end_of_day_m3": 732.9560000000005, "...": "..."},
    "schedule": ["... 96 rows ..."]
  },
  "optimized": {"status": "optimal", "valid": true, "schedule": ["... 96 rows ..."], "...": "..."}
}
```

Other cases that give `comparison_unavailable`:
- **No optimizer schedule:** the optimizer returns `infeasible` or `timeout_no_solution`. Then `optimized.schedule` is `[]` and the explanation says so (e.g. P1 unavailable, so P2 can't meet demand).
- **Baseline not applicable:** the fixed thresholds don't fit the tank (`baseline.applicable: false`), e.g. `capacity_m3: 900`.

### 13.5 Status values and HTTP codes

| HTTP | `status` | Body |
|---|---|---|
| 200 | `comparison_available` | Full body, as in §13.2. |
| 200 | `comparison_unavailable` | `peak_window` and `energy` are `null`; schedules and metrics are included where they exist. |
| 422 | `invalid_input` | `baseline`, `optimized`, `peak_window`, `energy` are `null`. `explanation` is the same message `/optimize` gives, e.g. `"missing 'peak_window'"`. |
| 422 | *(none)* | FastAPI's own `{"detail": [...]}` for non-JSON or non-object bodies, as for `/optimize` ([§4.3](#43-http-status-codes)). |
| 413 | `invalid_input` | Body over 256 KB. This body has the **`/optimize` shape** (it comes from the shared size limit), so check `status` before anything else. |
| 503 | `error` | 2 solves already running (shared with `/optimize`). Has a `Retry-After: 5` header; all comparison fields are `null`. |
| 500 | `error` | Optimizer or internal failure; all comparison fields are `null`. |

### 13.6 Display rules

1. **Always** show `label`, and make `caveats` visible (for example under an info icon).
2. Show reduction figures (`peak_window.*`, `energy.*`) **only** when `status === "comparison_available"`. Otherwise show `explanation` and each side's `violations`.
3. Label `reduction_kw` / `reduction_pct` as **peak-window demand (kW)**, e.g. "Simulated peak-window demand: 160 → 30 kW (−81%)". Never label it energy, kWh, cost or "savings".
4. If you show kWh at all, show `energy.note` next to it. Never present `optimized_minus_baseline_kwh` as efficiency savings.
5. Never show dollar, tariff or bill figures; the backend has none.
6. Round for display only; the API values are unrounded.
